# plant_keeper

Учебный REST API для учёта комнатных растений (TypeScript, Express). Проект создан как площадка для практики тестирования: часть багов в нём оставлена намеренно (см. раздел «Известные баги»).

Базовый адрес: `/api/v1`. Данные хранятся в памяти и при каждом запуске заново загружаются из JSON-файлов в `src/data` (сид), поэтому после перезапуска сервера все изменения сбрасываются.

## Запуск

1. Установить зависимости: `npm install`
2. Создать файл `.env` в корне проекта. Обязательные переменные:
    - `JWT_SECRET` — секрет для access-токенов
    - `JWT_REFRESH_SECRET` — секрет для refresh-токенов
3. Запустить в режиме разработки: `npm run dev`

Необязательные переменные (значения по умолчанию): `PORT` (3000), `NODE_ENV` (development), `JWT_EXPIRES_IN` (1h), `JWT_REFRESH_EXPIRES_IN` (30d), `BCRYPT_ROUNDS` (10), `DB_DRIVER` (memory).

Проверка работоспособности: `GET /api/v1/health`.

## Известные баги

Эти баги оставлены намеренно, для демонстрации тестов. **Исправлять их без отдельного решения не нужно.**

### BUG-1. Записи ухода принимают даты в будущем

- **Где:** `POST /plants/:plantId/care-logs` (а также `PATCH /plants/:plantId/care-logs/:logId`, если он включён в сборку)
- **Что происходит:** поле `occurredAt` проверяется только на формат ISO 8601. Дата в будущем принимается, запись сохраняется.
- **Ожидаемое поведение:** 400 `Validation failed` для даты позже текущего момента.
- **Последствия:** при записи полива с будущей датой у растения `lastWateredAt` становится датой в будущем.
- **Пример:**

```http
POST /api/v1/plants/{plantId}/care-logs
{ "type": "watering", "occurredAt": "2030-01-01T00:00:00.000Z" }
```

Фактический ответ: 201, у растения `lastWateredAt = 2030-01-01T00:00:00.000Z`.

### BUG-2. PATCH и PUT растения принимают любые поля (mass assignment)

- **Где:** `PATCH /plants/:id` и `PUT /plants/:id` (оба маршрута используют один обработчик)
- **Что происходит:** валидатор проверяет только перечисленные поля (`name`, `species`, `location`, `health`, `wateringIntervalDays`, `notes`) и не отбрасывает остальные. Тело запроса целиком записывается в растение.
- **Ожидаемое поведение:** лишние и служебные поля игнорируются или приводят к 400.
- **Последствия:**
    - можно сменить владельца (`ownerId`): растение пропадёт у текущего пользователя (404 при запросе) и появится у другого;
    - можно вручную подменить `lastWateredAt`, и он перестанет соответствовать записям ухода;
    - можно изменить `createdAt`;
    - можно сохранить произвольные несуществующие поля, и они вернутся в ответах.
- **Не затрагивает:** `id` и `updatedAt`: репозиторий задаёт их сам.
- **Пример:**

```http
PATCH /api/v1/plants/{plantId}
{ "ownerId": "22222222-2222-4222-8222-222222222222", "lastWateredAt": "2000-01-01T00:00:00.000Z", "foo": "bar" }
```

Фактический ответ: 200, в теле растения новый `ownerId`, `lastWateredAt` и поле `foo`. После этого `GET /plants/{plantId}` от имени исходного владельца возвращает 404.
